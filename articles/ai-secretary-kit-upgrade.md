> [1本目](https://zenn.dev/hobomokha/articles/9381d939aef2bd)でAIの記憶を置く「箱」を作り、[2本目](https://zenn.dev/hobomokha/articles/e4225ad7811e4b)で、育てると必ず散らかるという話をした。
> 今回は、その先の4か月でできあがった仕組みを、**まるごと渡せる形**にして公開する。

## はじめに：箱は育った。でも、世話が追いつかなくなった

1本目の記事で作ったのは、部品が3つだけの小さな箱だった。指示書の `CLAUDE.md`、自分のことを書く `master_profile.md`、テーマ別の `domains/`。

あれから4か月、毎日使い続けた。コミットは1,400回を超え、相談相手も Claude Code だけでなく Codex が加わった。AIは確かに自分のことを覚えていて、昨日の続きから話せる。そこは期待どおりだった。

期待と違ったのは、その先だ。

- 記録が増えるほど、AIが最初に読む量が増えて、話し始めるまでが重くなった
- 「次からこうして」と頼んだことが、次のセッションでは守られていなかった
- 同じ種類のミスを、日を変えて何度も指摘することになった
- 「反映しました」と言われたのに、実際には保存されていないことがあった

箱の中身は育っているのに、**箱の世話が追いつかない**。植物でいえば、鉢は大きくなったのに、水やりも植え替えも全部こちらが覚えていないといけない状態だ。

そこで4か月かけて、世話そのものを仕組みにしていった。この記事では、その仕組みを紹介し、最後に**あなたのAIエージェントに1文頼むだけで同じものが組み上がるキット**を渡す。

## この記事でできるようになること

- 4か月使って必要になった仕組みが、何を解決するものかが分かる
- Claude Code か Codex に1文頼んで、その仕組みを自分のリポジトリに組み上げられる
- 月に一度、点検と整理をエージェントに任せられる

1本目の箱をまだ作っていなくても大丈夫だ。空のリポジトリからでも始められる。すでに箱を育てている人は、いまの記録を残したまま仕組みだけを足せる。

## 1. いま、どうなっているか

先に全体を見てしまおう。1本目の箱と、いまの形を並べる。

```text
【1本目の箱】                     【いまの形】
CLAUDE.md                         CLAUDE.md / AGENTS.md     入口（数行だけ）
master_profile.md                 OPERATING_RULES.md        共通ルールと「掟」
domains/                          context_index.md          地図
                                  contexts/                 今回読むもの・読まないもの
                                  master_profile.md         正典
                                  domains/                  テーマ別の記録
                                  tools/ tests/             番人（検査と片付け）
                                  .claude/ .github/         番人を自動で動かす設定
```

ファイルは増えた。でも考え方は4つしかない。図書館にたとえると分かりやすい。

| 部品 | 図書館でいうと | 解決すること |
|---|---|---|
| 地図 | 館内の案内図 | 「この話、どこに書いたっけ？」 |
| 読まないものリスト | 「今日はこの棚だけ」という貸出票 | 読む量が増え続ける |
| 番人 | 出口のゲート | 頼んだ約束が守られない |
| 改善ループ | ご意見箱と、その集計 | 同じミスを何度も指摘する |

順番に見ていく。

### 地図：どこを読み、どこへ書くか

2本目の最後に予告した「地図」だ。`context_index.md` というファイルに、相談のテーマごとに1行で書いてある。

```markdown
| トピック・きっかけ | 入口 | 新しい情報の保存先 |
|---|---|---|
| 仕事・キャリアの相談と振り返り | bundle `work` | `domains/work.md` |
| 生活・趣味・日々の気づき | bundle `life` | `domains/life.md` |
```

AIは毎回この表から1行選び、そこだけを見にいく。書く場所も同じ行に決めてあるので、同じ話が3つのファイルに散らばることがなくなる。

ここで一つ失敗した。地図を丁寧に書こうとして、同じ対応表を4か所に書いてしまったのだ。READMEにも、読む用の表にも、書く用の表にも。新しいテーマを足すたびに4か所を直すことになり、どこかが必ずずれた。いまは**1か所だけ**に書き、ほかの場所からは指すだけにしている。

### 読まないものリスト：読む量を守る

記録が増えると、AIは「念のため」で関係ないファイルまで読む。丁寧に見えるが、遅くなり、費用がかさみ、古い情報を拾って答えがずれる。

そこでテーマごとに「必ず読む」「必要なら読む」「**通常は読まない**」を決めた。これを bundle と呼んでいる。

```markdown
## work

必須:
- `domains/work.md`

任意:
- `master_profile.md`

通常は読まない:
- `domains/life.md`
- `domains/_archive/`
```

意外だったのは、効くのが3つ目だということだ。読むものの一覧をいくら整えても、読む量は減らない。**読まないものを書いて、はじめて減る。**

### 番人：文章の約束を、機械に守らせる

これがいちばん大きな学びだった。

AIに「次からは必ず確認してから保存して」と頼む。AIは「承知しました」と答え、ルールとして書き留める。でも次のセッションでは、そのルールを読んでいても、**その瞬間には思い出さない**。人間でも同じだ。規則集に書いてあることと、その場で体が動くことは別の話だ。

実際、同じ種類のミスに対して「ルールを書き足す」を2回やって、3回目が起きた。そこでやり方を変えた。**繰り返したミスは、文章ではなく検査にする。**

| いつ | 番人がすること |
|---|---|
| 話し始める時 | 前回の宿題や、放置されている指摘があれば最初に知らせる |
| 保存を送る直前 | 存在しないファイルへの案内、地図のずれ、太りすぎを見つけたら、送信そのものを止める |
| 話を終える時 | 保存し忘れ・送り忘れが残っていたら、終了を一度止める |
| 毎週月曜の朝 | 誰も何もしなくても見回り、放置されたものをGitHubのIssueで知らせる |

たとえば、存在しないファイルを指したまま保存を送ろうとすると、こうなる。

```text
[pre-push] running check_references.py ...
[check_references] 1 problem(s):

  domains/work.md:27: `domains/does_not_exist.md` — file not found
[pre-push] BLOCKED: check_references failed. Fix the errors above before pushing.
```

AIが忘れていても、気を抜いていても、止まる。こちらが覚えておく必要がない。これが「世話を仕組みにする」ということだ。

:::message
**番人は、特定のAIに依存しない**

番人の本体は、ただのPythonスクリプトだ。Claude Code では自動で呼ばれるように設定し、その仕組みが無い Codex では、作業の手順の中で同じスクリプトを実行させている。1本目では「この用途なら Claude Code」と書いたが、いまは Codex も毎日使っている。どちらも同じ共通ルールを読み、同じ番人に止められる。
:::

### 改善ループ：同じことを、二度言わせない

AIの動き方が気になったら、その場で言う。「結論から言って」「それ、前に話したよ」。

言われたAIは、次の作業に進む前に、その言葉を**1行だけ**記録する。原因の分析はあとでいい。まず落とさないことを優先する。

```markdown
| 日付 | カテゴリ | 言われたこと（逐語寄り） | 文脈 | 状態 |
|---|---|---|---|---|
| 2026-10-16 | `参照ミス` `聞き直し` | 「それ前に話したよ」 | 仕事の相談中 | `raw` |
```

`raw`（未処理）のまま残っていると、次に話し始めた時に番人が知らせる。

```text
【⚠️ 未処理のフィードバックがある】
  | 2026-10-16 | `参照ミス` `聞き直し` | 「それ前に話したよ」 | 仕事の相談中 | `raw` |
  → 他の作業より先に、原因を直して状態を 反映済 / 不採用 へ進める
```

原因を直す時の順番も決めてある。

1. 機械で止められないか（番人を足す）
2. 使う瞬間に目に入る場所へ置けないか（その作業で必ず開く雛形）
3. いまあるルールを直すことで済まないか
4. それでも足りない時だけ、文章のルールを足す

文章のルールが最後なのは、さっき書いたとおり、いちばん効かないからだ。

この記事を書いている時点で、4か月で受けた指摘は118件、原因まで掘った失敗の記録は113件ある。そこから「これだけは常に守る」という**掟を14項**に蒸留して、共通ルールの先頭に置いている。たとえばこういうものだ。

:::details 掟の例（14項のうち5つ）
- 完了報告は、差分や検査結果などの確認とセットで行う。実行していないことを実行済みと報告しない。
- 保存を送っただけでは完了ではない。本流に入ったことを確かめるまでが完了。
- ファイルにある情報を、本人に聞き直さない。聞く前に読む。
- 繰り返したミスは、ルールの追記で塞がず、機械で止める。
- ルールの総量は予算制。足す前に、まとめることと削ることを考える。
:::

どれも、実際に痛い目を見てから書いたものだ。キットにはこの14項を出発点として入れてあるが、あなたの掟は、あなたのリポジトリで起きた失敗から育つ。

## 2. それでも太る。だから「予算」を決めた

仕組みを足していくと、今度は仕組みそのものが太る。

つい先日、まとめて測ってみた。AIが話し始める前に必ず読むファイルが、推定で約14,000トークン。指摘や失敗を記録するログ3本は、合計で約101,000トークンあった。ログは追記のたびに開くファイルなのに、処理の終わった古い記録が、そのまま残り続けていたのだ。

「古い記録は四半期ごとに片付ける」というルールは、ちゃんと書いてあった。そして、決めてから最初に来た期限で、もう実行されなかった。片付ける前に「教訓を取りこぼしていないか確認する」という重い作業を条件にしていたので、誰も手を付けなかったのだ。

ここでも答えは同じだった。文章ではなく、数値と検査にする。

- 毎回読むファイルと3本のログに、**大きさの上限**を決める
- 上限を超えたら、番人が保存の送信を止める
- ログは、コマンド1つで古い記録を別のファイルへ移す。移す前後で1件も欠けていないことを自動で確かめる

```text
[rotate_ops_logs] incident log: 45765 → 7415 トークン（74件中 61件を退避: 2026Q3 55件, 2026Q4 6件）
```

結果はこうなった。

| | 整理前 | 整理後 |
|---|---:|---:|
| 話し始める前に必ず読む量 | 約14,100 | 約7,600 |
| ログ3本 | 約101,500 | 約17,900 |

数字は、英数字4文字と日本語1文字をそれぞれ1トークンと数える概算だ。正確な値ではないが、同じ物差しで増えた・減ったを比べるには十分に使える。

大事なのは、これが**一度きりの大掃除で終わらない**ことだ。上限がある限り、太ればまた止まる。片付けを覚えておく必要がない。

## 3. 手を動かす：エージェントに1文頼む

ここからが本題だ。この仕組みを、個人の内容を抜いて書き起こし、キットとして公開した。

https://github.com/hobomokha/ai-secretary-kit

### 用意するもの

- GitHubの **private** リポジトリ（空でも、1本目の箱でもよい）
- Claude Code または Codex
- Git と Python 3.9以上（追加のインストールは要らない）

### 頼み方

自分のリポジトリをエージェントで開き、次の文をそのまま送る。

```text
https://github.com/hobomokha/ai-secretary-kit を取得して、SETUP.md の手順に従い、このリポジトリを秘書リポジトリとして構築してください。
```

これだけだ。キットの中の `SETUP.md` は、人ではなく**エージェントが読むための手順書**として書いてある。エージェントは次の順で進める。

1. リポジトリが private かを確かめる（public なら、そこで止まる）
2. キットを一時的な場所へ取得し、その版が動くかを自分で検査する
3. あなたに4つだけ質問する（よく相談する領域、使うエージェント、タイムゾーン、GitHub Actions を使うか）
4. ファイルを置く。**すでにある記録は残す**
5. 領域に合わせて、地図と読まないものリストを書く
6. 検査を全部通す
7. 保存して、動くところをあなたと一緒に確かめる

:::message alert
**すでに箱を育てている人へ**

`master_profile.md` や `domains/` の中身は上書きされない。古い `CLAUDE.md` に書いてあった指示は、共通ルールと見比べて、無いものだけが移される。心配なら「PRを作ったところで止めて、差分を見せて」と付け加えればいい。
:::

### うまくいったかの確かめ方

エージェントの「できました」を信じる前に、自分の目で3つ確かめよう。これは掟の1つ目そのものだ。

**1. 検査が通っている**

```bash
python3 tools/repo_ops/check_references.py
```

```text
[check_references] All checks passed.
```

**2. 太っていない**

```bash
python3 tools/repo_ops/context_budget.py
```

```text
[context_budget] 推定トークン / 上限
  ok      198 / 400    CLAUDE.md
  ok     4010 / 5200   OPERATING_RULES.md
  ok     1031 / 2900   context_index.md
  ...
```

**3. 新しいセッションで、番人が話しかけてくる**

セッションを開き直すと、最初にこういう報告が出る。

```text
=== セッション開始: 2026-10-16 ===

[repo_preflight]
  branch: main
  dirty: no
  upstream: origin/main
  divergence: ahead=0, behind=0
```

警告が何も無ければ、それが正常だ。

## 4. 違いを確かめる

仕組みが入ったら、わざと試してみてほしい。入れる前との差が、いちばんよく分かる。

**試すこと1：注文をつける**

何か相談したあとで、「結論から先に言って」と言ってみる。エージェントは返事を直すだけでなく、その言葉を記録し、原因（あなたの好みがどこにも書かれていなかった）を直そうとするはずだ。仕組みが無い時は、その場で直って、次のセッションで元に戻っていた。

**試すこと2：数えてみる**

```bash
python3 tools/repo_ops/pdca_report.py
```

いまの1件が数えられている。1か月後にもう一度実行すると、月ごとの件数と、**繰り返している種類の指摘**が出る。「減ったか」を感覚ではなく数で見られる。

自分のリポジトリで数えてみて、気づいたことがある。今月に入ってからの指摘35件のうち、AIの動き方そのものへの指摘は2件だけだった。残りは「この曲がいい」「文字を黄色に」といった、作っているものへの好みだ。先月は36件のうち17件が動き方への指摘だったので、どうやら減ってきている。数えるまで、これは分からなかった。

**試すこと3：壊してみる**

存在しないMarkdownファイルの名前（たとえば `domains/nothing.md`）を、どれかのファイルにバッククォートで囲んで書き、保存を送ってもらう。番人が止めるはずだ。止まったら、仕組みは生きている。確かめ終えたら、その1行は消しておこう。

## 5. 育て方：月に一度、点検を頼む

入れて終わりではない。でも、やることは少ない。

**日々**は、これまでと同じだ。相談して、区切りで「いまの話、覚えておいて」と頼む。気になったら、その場で言う。

**月に一度**、点検を頼む。依頼文はキットの `prompts/maintenance_request_prompt.md` に入っている。頼むと、エージェントは3つの数字を見る。

```bash
python3 tools/repo_ops/session_report.py --full      # 放置されているもの、古くなった情報
python3 tools/repo_ops/pdca_report.py                # 繰り返している指摘
python3 tools/repo_ops/context_budget.py --report    # 太ってきたファイル
```

すぐ直せるものは直し、あなたの判断が要るものは選択肢を付けて持ってくる。忘れていても、週次の見回りが「1か月以上、点検していない」とIssueで知らせてくる。

**重くなってきたら**、同じファイルにある「四半期の設計レビュー」の依頼文を使う。2章で書いた大掃除は、まさにこの依頼から始まった。AIに計測から頼み、数値で現状を出させ、直せるところを直させ、判断が要るものだけを持ってこさせる。

キットも、こちらで仕組みを直したら更新していくつもりだ。新しい版を取り込む手順も、エージェント向けに書いてある。

## 6. つまずきやすい点と、限界

**番人を増やしすぎない。** 検査は、足すたびに少しずつ窮屈になる。足すのは「同じミスが2回起きた時」だけにしている。1回目は、記録して様子を見る。

**常に鳴っている警報は、無いのと同じ。** 解決できない警告を出し続ける検査は、ほかの警告まで読まれなくする。実際に、どのセッションでも対処できない一覧を毎回表示していて、月次の点検でしか見ない場所へ移した。

**検査が見るのは形だけ。** 参照が切れていないか、太りすぎていないかは見るが、書いてある内容が正しいかは見ない。古くなった情報に `[FLOW]` の印を付け、月に一度見直すのは、いまも人とAIの仕事だ。

**エージェントは、それでも手順を飛ばす。** 番人は万能ではない。漏れたら指摘して、改善ループに入れる。完璧な仕組みを最初に作るのではなく、**漏れるたびに1つ塞ぐ**。4か月かかったのは、そのためだ。

**安全の基本は1本目と同じ。** リポジトリは必ず private にし、GitHubには2段階認証を設定する。パスワードやカード番号は、どんな理由があっても書かない。勤務先や顧客の詳細も要らない。「メーカーのマーケティング職」くらいの粒度で、十分に役立つ。

## まとめ

AIに記憶を持たせる箱は、1日で作れる。難しいのは、育てたあとの世話だった。

- **地図**で、どこを読み、どこへ書くかを1か所に決める
- **読まないものリスト**で、読む量を守る
- **番人**で、文章の約束を機械に守らせる
- **改善ループ**で、同じことを二度言わせない
- **予算**で、仕組みそのものが太るのを止める

どれも、うまくいかなかったことを1つずつ塞いでいった結果だ。最初から設計できたものは、1つも無い。

1本目の記事の最後に、**Δを感じたい**という話を書いた。変化を感じて、その差分を観測する楽しさ。4か月たって思うのは、差分を観測する相手が増えたということだ。AIが自分をどれだけ理解したかだけではなく、**自分とAIのやり取りそのものが、先月よりどれだけ良くなったか**も数えられるようになった。

キットは、その4か月ぶんの差分を詰めたものだ。そこから先のΔは、あなたのリポジトリで育ててみてほしい。
