> 連載「小さく作る意思決定RAG」の第3回です。
> [第1回](https://zenn.dev/hobomokha/articles/decision-rag-collect-episodes)で判断エピソードを集め、[第2回](https://zenn.dev/hobomokha/articles/decision-rag-build-knowledge-base)で承認済みデータをRAGへ入れました。今回は、一度登録した判断を置き換え、同じ質問で再評価します。

## 今回のゴール

この記事でやることは一つだけです。

**古い判断を新しい判断へ置き換え、RAGを再生成し、質問集で回答を評価する。**

本人が現在も判断を続けているなら、RAGも完成品として固定できません。経験によって考えが変わることもあれば、組織の役割や外部環境が変わり、以前の判断をそのまま使えなくなることもあります。

## Step 1：古い判断を上書きしない

第2回で使った `EP-001` の判断が、失敗や環境変化を受けて変わったとします。

Excelで次のように更新します。

1. `EP-001` の `validity` を `superseded` にする
2. `EP-005` を新しい行として追加する
3. `EP-005` の `validity` を `current` にする
4. `EP-005` の `supersedes_episode_id` に `EP-001` を入れる
5. 新しい回答、理由、例外、次回確認日を書く

```text
EP-001  validity=superseded
   ▲
   │ EP-005が置き換えた
   │
EP-005  validity=current
```

古い行を消さないのは、「以前はどう考えていたか」と「何が変わったか」を後から確認するためです。ただし、現在の相談に使うRAGへ入れるのは `current` の行だけにします。

:::message
過去の判断を保存することと、現在の回答へ使うことは別です。履歴として残しつつ、検索対象から外せる状態にします。
:::

## Step 2：Markdownを再生成する

第2回の変換コマンドを、もう一度実行します。

```bash
python3 csv_to_markdown.py episodes.csv data/episodes.md
```

確認することは2つです。

- `EP-001` が `episodes.md` から外れた
- `EP-005` が新しい判断として入った

本格的なRAGでは、この後にベクトルDBの更新、つまり再ベクトル化も行います。今回のローカルRAGは起動時にMarkdownを読み込むため、ファイルを置き換えて再実行すれば確認できます。

同じ質問をします。

```bash
python3 rag.py --compare "新しい企画は完成してから相談した方がよいですか？"
```

元データの変更が検索対象と回答へ反映されれば、RAGは「一度作った知識箱」ではなく、判断と一緒に育てる仕組みだと分かります。

## Step 3：回答用データと一緒に試験問題を作る

RAGデータだけを増やすと、改善したのか壊したのか判断できません。評価質問もCSVやExcelの別シートへ残します。

| 列 | 例 |
| --- | --- |
| `situation` | 企画レビュー会議、安全確認が必要 |
| `question` | 新しい企画は完成してから相談した方がよいですか |
| `expected_episode_id` | EP-005 |
| `expected_context_tags` | 完成前、安全確認 |
| `must_include` | 新しい判断で求める行動 |
| `must_not_say` | 置き換え前の古い方針 |
| `result` | 合格 / 要修正 |
| `notes` | 例外条件が回答から抜けた |

少なくとも、次の4項目を別々に見ます。

1. **検索評価**：期待したエピソードが取得されたか
2. **状況評価**：質問だけでなく、場面や制約の近さを拾えたか
3. **鮮度評価**：置き換え済みでなく、現在有効な判断を使ったか
4. **回答評価**：取得した内容を外さず、余計な断定をせず答えたか

検索に失敗しても、LLMが一般論でそれらしい文章を書くことがあります。反対に、正しいエピソードを検索できても、回答で重要な例外が落ちることがあります。

「良い答えだったか」だけでなく、**何を検索し、どの根拠から答えたか**を分けて確認します。

## Step 4：「分からない」質問も試す

正答例だけでは、RAGの安全性を確認できません。

- 収集対象外の人事評価を聞く
- 利用範囲が `restricted` のエピソードに近い質問をする
- 根拠が一件もないテーマを聞く
- 古い `EP-001` を前提に質問する
- 本人の正式判断と、第三者の解釈が食い違う質問をする

期待するのは、何にでも本人らしく答えることではありません。

```text
参照できる判断記録がありません。
現在の責任者へ確認してください。
```

このように、根拠がなければ保留できることも品質です。

## Step 5：更新のきっかけを決める

更新には、少なくとも3種類のきっかけがあります。

| きっかけ | 例 | 対応 |
| --- | --- | --- |
| 定期確認 | 四半期のレビュー日が来た | `next_review_date` の行を確認する |
| 出来事 | 方針変更、失敗、新しい例外、役割変更 | 新しいエピソードを追加する |
| 利用結果 | 欲しい事例が検索されない、回答が違う | ログを確認して不足データを集める |

```text
新しい判断・利用者の指摘
          │
          ▼
     pendingで収集
          │ 本人・責任者・出典で確認
          ▼
 approved + current
          │ 古い行はsupersededへ
          ▼
 Markdown再生成 → 再ベクトル化 → 質問集で再評価
```

運用担当者が勝手に「本人らしい答え」を書き足すのではありません。入力者、確認者、利用範囲を決め、変更履歴を残します。

## 判断データの品質を確認する7項目

更新時は、次の7項目を確認します。

1. **具体性**：どの場面で、何を許し、何を求めたか
2. **出典**：誰の記憶か、どの記録か、いつの出来事か
3. **鮮度**：過去の発言と現在の方針が分かれているか
4. **例外**：「必ず」「絶対に」が本当に全場面へ当てはまるか
5. **反証**：同じ考えがうまくいかなかった事例もあるか
6. **視点**：本人、第三者、公式記録を区別しているか
7. **更新可能性**：誰が、いつ、何をきっかけに見直すか

成功談だけで作ると、RAGは相談相手ではなく標語生成器になってしまいます。判断を変えた事例や、例外を置いた事例も同じように重要です。

## 判断する人が交代した後は、二つを分ける

本人が判断の場を離れた後は、次の二つを区別します。

- **過去の本人がどう考えたか**を示す記録
- **現在の組織としてどう判断するか**を示す方針

これらを混ぜると、過去の発言が現在の正式判断であるように見えてしまいます。

承継後は、次を決めておきます。

- 本人の記録をどこまで凍結して残すか
- 現在の方針を誰が承認するか
- 両者が違う場合、回答画面でどう見せ分けるか
- 重要な判断を誰へ引き継ぐか

AIは過去の判断を参照しやすくできますが、現在の責任まで引き受けるわけではありません。

## 発注者とベンダーは、どこを一緒に作るのか

| 組織側が主に決めること | ベンダーが支援できること |
| --- | --- |
| どんな相談に使うか | ユースケースを質問集へ分解する |
| 何が現在の正式な判断か | ヒアリング設計を支援する |
| 矛盾する発言のどちらを採るか | 矛盾・重複・欠損を検出する |
| 誰の同意が必要か | 承認フローと権限制御を作る |
| 誰にどこまで見せるか | メタデータ検索とアクセス制御を作る |
| 誰がいつ見直すか | 更新通知、版管理、再ベクトル化を自動化する |
| どの回答なら役に立つか | 評価画面と改善ログを作る |

ベンダーだけでは、ある発言が現在も正しいのか、どの失敗を残すのかを決められません。一方、組織側だけで検索・権限・監査の仕組みを作る必要もありません。

組織側がデータの意味と更新責任を持ち、ベンダーが安全に収集・検索・評価・更新できる仕組みにする。ここが役割分担の中心です。

## 10日間の小さな実験にする

| 時期 | やること | 成果物 |
| --- | --- | --- |
| 1〜2日目 | 対象テーマと場面付き質問を10個決める | 質問集 |
| 3〜5日目 | 本人・周囲・記録から話を集める | エピソード候補 |
| 6〜7日目 | 意図、例外、利用範囲、有効性を確認する | 承認済み4〜10件 |
| 8日目 | CSVからMarkdownを作りRAGへ入れる | 小さな知識ベース |
| 9日目 | 質問だけ／場面付き質問を比べる | 評価結果 |
| 10日目 | 1件を置き換え、同じ質問で再評価する | 更新手順と変更履歴 |

最初の成果は、高い正答率ではありません。

**どの質問へ答えたいのに、どのデータが足りないかを具体的に言えること**です。

## Digital MATSUMOTOとのつながり

Digital MATSUMOTOの公開リポジトリには、RAG用CSV、Markdown形式のページデータ、ChromaDB、RAGデータ更新、フィードバック保存などが含まれています。

```text
Digital MATSUMOTOの広い仕組み
  データ管理 + RAG更新 + 検索 + 会話 + フィードバック + 分析

今回の小さな実験
  エピソード収集 + 承認 + 現行データの書き出し
  + 質問評価 + 置き換え更新
```

3本の記事で行ったのは、そのデータ運用を理解するために最小化した体験です。

## 今回の完成条件

- 古い判断を消さず `superseded` にした
- 新しい判断へ置き換え関係を付けた
- Markdownを再生成し、検索対象が変わったことを確認した
- 評価質問で検索・状況・鮮度・回答を分けて見た
- 根拠がない質問では回答を保留できるか試した
- 定期・出来事・利用結果の更新担当を決めた

ここまで試すと、RAGはモデルを選んで終わるシステムではなく、**判断データを集め、確かめ、更新し続ける運用**だと分かります。
